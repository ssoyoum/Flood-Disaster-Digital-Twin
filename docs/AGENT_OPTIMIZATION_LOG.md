### 3-a. 도구 결과에서 지도용 필드 빼기 (O1)

- 문제: 오송 `get_reconstruction` 결과 12,154자 중 `envelope_comparison`(HAND 범위 비교, 5,614자)은 지도용이고, 카탈로그상 모델이 인용할 항목이 아니다. 서울 `trace_reveal`, 각 사건 `hand_reconstruction`도 같다.
- 바꾼 것: 모델에 보내는 결과에서만 뺀다. 근거 검사는 계속 전체 결과로 한다.
- 결과: 43/43 유지, 토큰 278,200 → 261,787(−5.9%). 재구성을 부른 6문항만 보면 −19.4%, 모델 응답 1회당 5,446 → 4,078 토큰(−25%). 근거 유효성·도구 정확도 1.0 유지.

### 3-b. 도구 카탈로그 중복 필드 빼기 (O2)

- 문제: 카탈로그의 영문 `description`·`output`·`input_fields`는 한글 `use_when`·`parameters`와 내용이 겹친다(시설 도구는 같은 문장).
- 바꾼 것: 모델에는 `name·use_when·parameters·can_say·cannot_say·examples`만 보낸다. 카탈로그 36~43% 감소.

## Ollama 도입 (로컬 모델 비교)

- 목적: 네트워크·API 키 없이 돌릴 수 있는 대안과 비교 기준. 공개 서버 기본값은 Gemini를 유지한다(AWS 크레딧 한도로 서버 사양을 올릴 수 없음). `AGENT_LLM_PROVIDER=ollama` 한 줄로 바뀌며 프롬프트·도구·검증은 같다.
- 환경: Ryzen 5 4500U CPU(외장 GPU 없음), `qwen2.5:3b`, 판단 1회 15~180초.
- 같은 대표 13문항, 같은 코드에서 3단계 축소만 켬/끔:

| | O1·O2 끔 | O1·O2 켬 | Gemini(참고) |
| --- | --- | --- | --- |
| 통과 | 8/13 | **11/13** | 13/13 |
| 프롬프트 토큰 | 96,449 | **82,034 (−14.9%)** | — |
| 응답 1회당 프롬프트 | 3,445 | 2,930 | — |
| 판단 1회 중앙값 | 44 s | 49 s | 1~5 s |

- 읽는 법: 프롬프트는 15% 줄었지만 속도는 빨라지지 않았다. 판단 시간이 같은 문항 안에서도 15~180초로 흔들려 이 실행으로는 속도 효과를 판단할 수 없다. 통과 8 → 11도 13문항이라 우연을 배제하지 못한다.
- **작은 모델이 서버 규칙의 빈틈을 드러냈다.** 근거 검사에서 떨어진 답이나 같은 호출 반복으로 루프가 멈춘 경우, 필요한 도구 결과가 있어도 `NEEDS_DATA`가 됐다. 모델 시간 초과 뒤 대체 경로에서는 예보·가정 질문 규칙이 빠져 `ANSWERED`가 됐다. 셋 다 서버 규칙으로 막았다(회귀 테스트 추가). Gemini에서는 드물게만 나오던 경로다.

## 4단계. 전체 경로 병목 찾기 (Stage 5)

**한 줄:** 브라우저부터 도구까지 시간을 쪼개 보니 병목은 모델이 아니라 **첫 호출의 자료 적재**였다. 미리 적재하면 빨라지지만 서버 메모리 상한 때문에 채택하지 않았다.

| 구간 | 측정값 | 측정 방법 |
| --- | --- | --- |
| 브라우저 ↔ API 왕복(서버 처리 제외) | 30~80 ms | `e2e/agent-latency.spec.ts` |
| 응답 → 화면 표시 | 17~69 ms (23 KB 응답도 42 ms) | 〃 |
| 모델 판단 1회 | Gemini 1~5 s / Ollama CPU 15~180 s | trace |
| 도구 첫 호출 → 두 번째 | 기준 비교 8,316 → 41 ms, 반경 재고 5,545 → 26 ms, 연구 모델 3,112 → 1 ms, 서울 재구성 1,219 → 5 ms | `profile_path.py` |
| 브라우저에서 본 첫 호출 | 반경 재고 14.4 s, 기준 비교 10.4 s (두 번째 82 ms) | E2E |

- 가설(H1): "첫 요청의 도구 지연은 자료 적재이고, 서버 시작 때 미리 적재하면 사라진다." → 시간은 맞았다(두 번째 호출 수십 ms).
- 대가: 메모리. import 197 MB → 도구 자료 전부 적재 491 MB(+294) → 요청·지도 캐시까지 611 MB(서울 재구성 +109, 연구 모델 +88, 기준 비교 +60, 반경 재고 +32). 공개 서버 컨테이너 상한은 600 MB다.
- 결정: **미리 적재하지 않는다.** Agent를 안 쓰는 방문자에게도 300 MB를 상시로 쓰게 되고 상한에 닿는다. 보드의 «통제 기준 검토» 탭을 열면 같은 캐시가 채워지므로 실제 흐름에서는 Agent 질문 전에 데워지는 경우가 많다. 대신 재배포 전에 컨테이너에서 메모리를 다시 재는 일을 TODO 위험 항목으로 올렸다.
- 발표 메시지: "측정 없이 '캐시 미리 올리기'를 넣었다면 서버가 메모리 상한에 걸렸을 것"이라는, **채택하지 않은 최적화도 측정 결과**라는 사례.

**배포 이미지로 다시 잰 메모리 (로컬 Docker, 같은 `Dockerfile.aws`)**

| 단계 | 컨테이너 메모리 |
| --- | --- |
| 시작 | 277 MiB |
| 네 사례 지도 | 477 MiB |
| 보드(상태·백테스트·기준 검토·연구 모델) | 538 MiB |
| Agent 오송 도구 | 635 MiB |
| 서울 2022 지도 | 664 MiB |
| 최대(`memory.peak`) | **765 MiB** |

공개 서버 컨테이너 상한 600 MB로 띄우면 상한에 1,086번 닿고 482 MB를 스왑으로 밀어내 Agent 요청이 120초를 넘겼다. 미리 적재를 하지 않아도 **기능을 모두 쓰면 이미 상한을 넘는다**는 것이 이번 측정의 가장 큰 발견이었다.

## 5단계. 메모리 — 600 MB 서버에서 죽지 않게

**한 줄:** 단계별로 메모리를 재다가 **같은 오송 자료(약 140 MB)를 캐시 키 차이로 반복해서 다시 읽는 버그**를 찾았고, 고친 뒤 스왑 없는 600 MB 컨테이너에서 OOM 종료가 사라졌다.

| 시도 | 바꾼 것 | 결과 |
| --- | --- | --- |
| ① | 지도 응답 캐시를 gzip만 남기고, 읽기 전용 호출은 `deepcopy` 없이 공유 캐시 사용 | 상시 RSS 689 → 627 MiB, 최대 791 → 699 MiB. 여전히 600 초과 |
| ② | `MALLOC_ARENA_MAX=2`(환경 변수 1개) | 상시 551, 최대 634 MiB. 스왑 없는 600 MB에서 **여전히 OOM** |
| ③ | 단계별 측정: 지도를 만든 뒤 첫 Agent 질문에서만 파이썬 힙 +112 MB | 원인: `get_osong_repository()`와 `get_osong_repository(2023)`가 `lru_cache(maxsize=1)`의 **다른 키**라 지도·Agent 호출이 번갈아 서로를 밀어내고 같은 자료를 다시 파싱 |
| ④ | 캐시를 인자 없는 내부 함수 하나로 통일 | 첫 질문 순간 증가 0, 스왑 없는 600 MB **통과** |

| 스왑 없는 600 MB 컨테이너(EC2와 같은 조건), 네 사례 지도 → 보드 → Agent 도구 전부 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 결과 | **첫 Agent 질문에서 OOM 종료(exit 137)** | **통과, 상한 도달 0회** |
| 정착 메모리(`docker stats`) | 663~697 MiB(상한 없이 잼) | **506 MiB** |
| 프로세스 RSS / 최대 RSS | 689 / 791 MiB | **533 / 605 MiB** |

- ②는 ④ 이후 효과가 약 16 MiB로 줄어 채택하지 않았다(③의 반복 파싱이 남긴 단편화를 가리던 효과였다).
- 덤: 같은 버그가 trace에서 보였던 "오송 라우터 단계 가끔 1~5초"의 원인 후보다(재파싱).
- 남은 큰 덩어리: `lightgbm` import 88 MB(한 행 예측용), 오송 지도 파싱 143 MB, 서울 지도 113 MB. 연구 모델 파일은 다른 작업이 진행 중이라 손대지 않았다.
- 발표 메시지: **"최적화는 감이 아니라 측정에서 나온다."** 캐시를 늘리는 대신 재서 보니, 캐시가 같은 자료를 두 번 들고 있었다.

## 부록: 모델 할당량이 끝나도 서버가 답한다

Gemini 일일 할당량 소진(HTTP 429)으로 모든 모델 요청이 막힌 실행에서도 43문항 중 37개가 서버 경로(등록 도구 결과·고정 거절 문구)로 올바른 상태를 냈다. 실패 6개는 원래 모델이 있어야 하는 문항이다.
