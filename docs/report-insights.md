# FloodOps 작업 인사이트

> 작성일: 2026-09-04  
> 대상: 과제 기획안·발표·포트폴리오 보고서

## 1. 프로젝트의 핵심 인사이트

FloodOps의 핵심 가치는 침수 결과를 단순히 지도에 표시하는 데 있지 않다. 관측값, 지형 분석값, 시설 재고, 운영 규칙을 구분해서 보여주고, 담당자가 **왜 이 시설을 먼저 확인해야 하는지** 판단할 수 있게 만드는 데 있다.

따라서 화면의 우선순위는 다음과 같이 정리했다.

1. 현재 위험과 즉시 조치가 필요한 대상
2. 해당 판단의 근거가 되는 관측·분석 데이터
3. 반경 내 시설 재고와 참고용 통계

반경별 건물·도로·시설 수는 노출 가능성을 파악하는 보조 자료다. 공식 침수범위와 중첩해 계산한 피해 추정치가 아니므로, 피해 규모처럼 오해되지 않도록 `Exposure inventory · secondary`로 명시해야 한다.

## 2. 데이터 신뢰도와 표현에 대한 인사이트

이번 구현에서 가장 중요한 데이터 품질 이슈는 **관측소 수위와 DEM 표고의 기준면이 다를 수 있다는 점**이었다.

- `observed_water_level_m`: 관측소에서 측정된 수위
- `relative_water_level_rise_m`: 기준 시점 대비 수위 상승분
- `hand_m`: 지형의 배수로부터의 상대 높이(HAND)
- `hand_threshold_m`: 분석에 사용한 선택 임계값
- `mean_elevation_m`: DEM 기반 평균 표고
- `local_drainage_elevation_m`: 지역 배수 기준 표고

이 값들은 같은 단위인 미터로 표현되더라도 곧바로 서로 뺄 수 있는 값은 아니다. 특히 `10.03 m` 같은 관측 수위를 DEM 단면의 물 높이로 그대로 그리면 실제 침수심으로 오해될 수 있다. 현재 단면의 파란 영역은 실측 침수심이 아니라 **관측 수위 상승분을 이용한 대리 시각화**로 취급해야 한다.

보고서에는 다음과 같이 명시하는 것이 안전하다.

> 현재 시스템은 관측 수위 상승과 HAND 기반 지형 취약성을 결합해 위험 진행을 재현한다. 관측소 기준면과 DEM 수직 기준을 정합하는 자료가 확보되기 전까지 단면의 수면은 실제 침수심이 아닌 대리 표현이다.

이를 통해 화면의 시각적 설득력과 데이터의 과학적 정직성을 함께 확보했다. 향후 실제 침수심을 산출하려면 기준면 정합, 수위-표고 보정, 수리모형 또는 공식 침수범위 검증이 추가로 필요하다.

## 3. UI 설계에서 얻은 인사이트

정보를 한 화면에 모두 배치하면 기능은 많아 보이지만, 관제 화면의 판단 속도는 오히려 떨어진다. 그래서 UI2에서는 다음 원칙을 적용했다.

- 지도는 위험 위치와 진행 상태를 확인하는 공간으로 유지
- 왼쪽 패널은 Agent의 우선순위 판단과 조치 권고를 중심으로 구성
- Layers는 접을 수 있는 참고 영역으로 낮춤
- 상세한 시나리오 설명과 전후 비교는 `Scenario 비교` 페이지로 분리
- 데이터 해석과 한계·다음 검증 단계는 `인사이트` 탭으로 분리
- 지도 위에는 근거를 과도하게 겹쳐 표시하지 않고, 필요한 정보는 패널에서 확인

이 구조는 “지도 중심 화면”에서 “판단 중심 관제 화면”으로의 전환이다. 특히 Agent를 하단에 묻어두지 않고 판단 카드 바로 아래에 배치함으로써, 시스템의 차별점인 설명 가능한 의사결정을 시각적으로 드러냈다.

탭을 세 개의 업무 흐름으로 나눈 것도 중요한 설계 결과다.

- 관제 화면: 지금 무슨 일이 일어나고 있는가
- Scenario 비교: 개입하면 운영 상태가 어떻게 달라지는가. 원시 지도와 선택 지도는 40:40으로 크게 배치하고, Evidence & HAND section은 오른쪽 고정 레일로 유지한다.
- 인사이트: 어떤 데이터와 한계를 근거로 판단하는가

관제 화면의 상단 요약 칩은 축약형 Agent 입력창으로 대체했다. 반복되는 건물·도로·시설 총량보다 담당자가 바로 질문을 입력하고 조치 근거를 확인하는 흐름을 우선한 것이다. `Evidence & HAND section`은 탭 1 오른쪽에 원래 구성으로 유지하고, 동일 컴포넌트를 탭 2의 고정 근거 레일에서도 재사용해 관측·단면 정보의 일관성을 확보했다. 해석과 데이터 한계는 인사이트 탭에서 별도로 확인한다.

## 4. Scenario 비교 기능의 의미

시나리오 비교는 단순한 화면 전환이 아니라, **개입 전후의 운영 상태를 비교하는 실험 인터페이스**다.

- Baseline: 관측 재현 및 기존 운영 상태
- Intervention: 감지 후 차량 자동 차단 등 운영 개입 적용 상태
- 공통 조건: 같은 관측 시점, 같은 임계값, 같은 위험 진행 단계
- 비교 결과: 차량 진입 차단 여부, 조치 상태, 담당자 확인 대상

현재 레포 자료로 계산할 수 있는 것은 관측 타임라인 기반의 차단 시각 비교와 연결된 건물 ID 검증까지다. 개입 후 침수범위·침수심·교통/차량 노출·취약도 자료가 없으므로 `risk_reduction`, 전후 우선건물 수, 피해 감소율은 계산하지 않는다. API는 이 경우 `UNAVAILABLE`과 `null`을 반환하며, 임의 계수로 0 또는 감소율을 만들지 않는다.

향후 실제 `risk_reduction`을 제공하려면 개입별 효과 모델, 시설별 취약도, 시간에 따른 노출 변화, 교통/차량 데이터, 공식 침수범위 또는 검증된 수리학 모델이 필요하다.

## 5. Agent 기능에 대한 포트폴리오 관점의 인사이트

Agent는 원시 데이터를 대신 결정하는 기능이 아니라, 여러 근거를 연결해 담당자의 다음 행동을 제안하는 보조 계층이다.

이번 작업에서는 다음과 같은 역할 경계를 분명히 했다.

- 위험 단계와 임계값은 규칙 기반으로 재현
- Agent는 우선순위와 조치 이유를 설명
- 반경별 시설 재고는 추가 확인 질문을 통해 조회
- 공식 침수범위와 반경 재고를 동일한 의미의 피해 자료로 섞지 않음
- 모든 권고에는 근거 데이터와 데이터 성격을 함께 표시

이 경계 덕분에 Agent를 “그럴듯한 답변 생성기”가 아니라 **근거를 가진 운영 의사결정 인터페이스**로 설명할 수 있다. 향후 LLM을 연결하더라도 위험 판정의 기준과 원시 데이터 출처는 규칙·API 계층에 남겨야 한다.

## 6. Replay 기능의 의미

Replay는 애니메이션 효과가 아니라 동일한 사건을 다시 검토할 수 있는 검증 장치다.

- 관측 시점부터 위험 단계 변화까지의 순서를 재현
- 임계값 도달 시점과 운영 개입 시점을 비교
- 발표·시연 시 동일한 흐름을 반복 재생
- Agent의 권고가 어떤 단계에서 생성됐는지 확인

따라서 Replay는 실제 예측과 혼동되지 않도록 `관측 재현` 또는 `시나리오 재생`으로 표시하는 것이 적절하다.

## 7. 실행 환경 고정에서 얻은 인사이트

프론트와 백엔드의 주소가 프로젝트마다 바뀌면 기능보다 환경 설정에서 오류가 발생한다. 이번 작업에서는 로컬 실행 계약을 고정했다.

- 프론트: `http://localhost:5173`
- 프론트 대체 주소: `http://127.0.0.1:5173`
- 백엔드 Swagger: `http://localhost:8033/docs`
- 백엔드 Health: `http://localhost:8033/health`

Vite의 `strictPort`와 API fallback을 함께 설정해, 포트가 조용히 다른 번호로 이동하거나 잘못된 백엔드로 요청하는 문제를 줄였다. Docker 실행 포트와 로컬 개발 포트는 별개의 실행 모드이므로 문서에서도 구분했다.

## 8. 오늘 수행한 데이터 엔지니어링성 조정

오늘 작업의 중요한 부분은 화면에 데이터를 연결하는 데서 끝나지 않고, 서로 다른 출처와 의미를 가진 데이터를 하나의 운영 흐름으로 정리한 것이다.

### 8.1 데이터 계약과 타입 정리

프론트엔드가 임의의 숫자를 만들지 않도록 API 응답을 타입으로 고정했다. 이벤트, 레이어, 관측값, 재구성 단계, 시나리오 실행 결과를 각각 분리하고, 레이어마다 `status`, `source`, `snapshot`, `feature_count`, `geometry_types`, `data`를 함께 전달하는 구조를 사용했다.

이를 통해 지도 레이어와 분석 카드가 같은 원천 응답을 바라보게 되었고, `VERIFIED`, `DERIVED`, `TEMPORARY` 같은 데이터 상태도 UI에서 일관되게 표현할 수 있게 되었다.

### 8.2 원시값·파생값·대리값의 분리

`hand_reconstruction` 레이어의 속성을 기준으로 단면을 구성하도록 연결했다. `hand_m`, `observed_water_level_m`, `relative_water_level_rise_m`, `hand_threshold_m`, 표고, 강우량을 한 셀의 분석 맥락으로 묶되, 각각의 역할은 분리해서 표시했다.

- 원시/관측값: 관측 수위, 시간당 강우량
- 지형 분석값: HAND, 평균 표고, 배수 기준 표고
- 파생값: 선택 임계값, 위험 단계, 대응 여유
- 대리 표현: 단면의 파란 수면 영역과 Replay 위험 진행

이 구조는 향후 데이터가 교체되어도 화면의 숫자 출처를 추적할 수 있는 최소한의 데이터 lineage를 만든다. 또한 공식 침수범위가 없는 상태에서 임시 envelope를 공식 피해 결과처럼 소비하는 것을 방지한다.

### 8.3 레이어와 분석 결과의 정합

지도에는 AOI, 하천, 도로, 건축물, HAND 재구성, 지하차도 등 필요한 레이어만 기본 노출하고, 시설 재고와 근사 envelope는 보조 정보로 분리했다. 레이어의 표시 여부를 토글할 수 있도록 하면서도, 지도 위에 모든 통계를 겹쳐 놓지 않고 패널과 비교 화면으로 분산했다.

이 조정은 단순한 UI 정리가 아니라, 공간 데이터의 역할을 `분석 기준`, `위험 시각화`, `노출 재고`, `운영 대상`으로 나누는 데이터 모델링 작업이다.

### 8.4 재현 가능한 시계열 구조

`reconstruction.replay`의 단계와 `baseline.states`를 기준으로 Replay와 Scenario 비교를 구성했다. 같은 이벤트의 동일한 단계 배열을 지도, 단면, 타임라인, 비교표가 공유하므로 각 화면의 시간이 어긋나지 않는다.

또한 Intervention은 같은 위험 진행을 전제로 차량 신규 진입 차단이라는 운영 상태만 바꾸도록 표현했다. 물리 모델이 없는 상태에서 침수 속도나 침수범위가 줄었다고 계산하지 않아, 데이터가 제공하는 범위를 넘는 결론을 만들지 않도록 했다.

### 8.5 실행 환경과 데이터 연결 경로 표준화

기존 프로젝트 간 포트 불일치로 잘못된 API에 연결될 수 있던 문제를 정리했다. Vite는 `5173`으로 고정하고 `strictPort`를 사용했으며, 프론트 API 기본 주소와 `.env.example`을 FloodOps 백엔드 `8033`에 맞췄다. Docker 포트와 로컬 개발 포트도 문서에서 구분했다.

이 작업은 배포 기능은 아니지만, 개발 환경에서 데이터 파이프라인의 입력 지점(API)과 소비 지점(프론트)을 고정해 재현성을 높인 조정이다. 서버가 꺼진 경우에도 아래 Health endpoint로 연결 상태를 빠르게 확인할 수 있다.

- 프론트: `http://localhost:5173`
- 백엔드 Health: `http://localhost:8033/health`
- 백엔드 Swagger: `http://localhost:8033/docs`

## 9. 구현 검증 근거

- 프론트 단위 테스트: 2건 통과
- 프론트 빌드: 성공
- 백엔드 테스트: 58건 통과
- 로컬 프론트 응답: `5173`에서 200
- 백엔드 Health 응답: `8033/health`에서 200
- 이벤트 API 응답: `8033/api/events`에서 정상 응답, 이벤트 5건 확인

단, 브라우저 기반 실제 시각 QA는 별도 검증 항목으로 남겨두었다. 빌드 성공은 컴파일 가능성을 증명하지만, 지도 렌더링·반응형 배치·애니메이션 체감까지 보장하지는 않는다.

## 10. 보고서에 사용할 수 있는 한 문장

> FloodOps는 침수 데이터를 많이 보여주는 시스템이 아니라, 데이터의 신뢰도와 의미를 구분한 상태에서 관측 재현·근거 기반 Agent·개입 전후 시나리오 비교를 제공해 담당자의 다음 조치를 빠르게 만드는 운영형 디지털 트윈이다.
