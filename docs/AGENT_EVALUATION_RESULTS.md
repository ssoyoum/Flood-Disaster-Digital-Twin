# Agent 연결·대조 검증 기록

검증일: 2026-10-09 KST. 대상: 현재 로컬 작업 트리의 `/api/agent/ask`와 직접 분석 API. 공개 서버 배포 검증이 아니다.

## 등록 도구 경로

`backend/evaluation/agent_ask_cases.json`의 **13개 대조 검사 모두 통과**했다. 네 사건의 기본 질문 6개, 조건 재사용·변경 5개, 모호한 조건 2개다. 모델을 사용하지 않았으며 도구 결과 11개·조건 확인 2개로 구분한다.

검사 내용은 HTTP 응답, 사건 ID, 조건 선택, 도구명·실행 파라미터, 직접 분석 API의 시나리오 또는 저류 수치다. Assistant가 제시한 다른 숫자가 있는 대화도 포함한다. 단순 HTTP 200 확인을 성공으로 계산하지 않았다.

## 실제 Gemini 소수 질문

기본 모델 `gemini-3.5-flash-lite`로 아래 4건을 실행했다. 3건은 도구 호출 후 모델 설명을 완성했고, 1건은 조건 확인 경로로 모델을 호출하지 않았다. HTTP 모델 요청은 총 **6회**, 등록 도구 폴백은 **0건**이었다.

| 질문 | 조건 처리 | 직접 분석 대조 | 모델 설명 | API 소요 시간 |
|---|---|---|---|---|
| 08:20에 통제했다면? | 이번 질문의 08:20 | 유입 전 7분 일치 | 완료 | 9,797ms |
| 앞선 사용자 08:20 질문 뒤 “그 조건으로 다시 비교해줘” | 사용자 08:20 재사용, Assistant의 08:00 제안 제외 | 유입 전 7분 일치 | 완료 | 3,938ms |
| 앞선 사용자 08:20 질문 뒤 “그럼 08:10은?” | 08:10으로 변경 | 유입 전 17분 일치 | 완료 | 3,484ms |
| 통제 08:20·유입 지연 10분 질문 뒤 “그 조건으로 다시 비교해줘” | 복합 조건 확인 요청 | 분석 실행 없음 | 모델 미호출 | 0ms(반올림) |

실제 답변을 읽어 08:27 유입, 08:35 주행불능과의 시간차가 도구 값과 일치함을 확인했다. 답변은 재구성 시각이라는 단서를 포함하고 차량 대피·침수 감소량을 계산하지 않았다고 설명했다. 해당 시각의 공식 원문 페이지 확인 과제는 계속 남아 있다.

이는 **오송의 제한된 질문 점검**이다. 서울·포항·안동의 실제 모델 대조, 물리 효과 질문, 다양한 한국어 표현, 장시간 반복 사용, 공개 배포·동시 부하 안정성은 아직 이 결과로 검증되지 않았다. 3건 성공을 서비스 전체의 성공률·만족도로 발표하지 않는다.

## 재현과 원본

```powershell
python backend/evaluation/evaluate_agent.py --output docs/local/agent-eval-offline-20261009.json
python backend/evaluation/evaluate_agent.py --mode live --case osong-closure --case reuse-closure --case update-closure --case ambiguous-combined --output docs/local/agent-eval-live-20261009.json
```

각 JSON은 비공개 로컬 원본이며 답변, 도구 입력, 요청 ID, 단계·HTTP 수, 실패 코드, 검사 결과를 포함한다. API 키는 기록하지 않는다. 다시 실행하면 모델 문장과 소요 시간은 달라질 수 있다. live 명령은 실제 모델의 요청량을 사용한다.

### trace로 찾은 문제 (2주차 후보)

1. **근거 검사의 거짓 거부** — 서울 저류 2문항(s-seoul-storage, w-seoul-storage-damage)이 도구 정상·모델 답변 정확인데 `answer_not_grounded`로 `NEEDS_DATA`가 됐다. 같은 질문을 다시 보내 모델 원문을 확인했다. `_grounded_answer`가 숫자를 도구 결과 JSON 문자열에서 찾기 때문에 `1,242,453`·`400,000`(천 단위 쉼표)이 `1242453`·`400000`과 맞지 않고, `20:59`(첫 구조 신고)는 도구 설명에만 있고 결과에는 없다.
2. **실패한 도구의 반복 호출** — 도구가 예외를 내면 모델이 같은 호출을 5번 반복해 모델 판단 6회를 다 쓴다. 도구 실패 3문항이 모델 요청 7·6·6회, 전체 83회의 23%를 썼다. 반복 호출은 live 전체에서 19번 나왔다(시설 "왜" 질문도 3번).
3. **값 없는 가정의 상태** — "통제를 더 일찍 했다면?"(a-no-value)에 모델이 재구성 시각만 인용하고 `gap_kind` 없이 답해 `ANSWERED`가 됐다. 답변 내용은 "시각이 없어 계산할 수 없다"인데 상태는 답한 것으로 나온다.
4. **모델 장애 시 거절 경로** — 물리 효과·예보 질문은 모델이 있어야 올바른 `NEEDS_DATA`가 된다. 서버만으로 판정 가능한 질문(`_is_physical_effect_question`)인데 모델 장애에서 `UNAVAILABLE`로 끝난다.
5. **비용·지연** — 토큰의 95.7%가 프롬프트(도구 카탈로그·관측 결과)다. 첫 요청의 자료 적재가 지연 꼬리를 만든다: 반경 재고 5.5 s, 관측 요약 3.7 s, 오송 통제 질문의 라우터 단계 0.9~1.5 s(offline trace).

## Ollama A/B와 전체 경로 측정 (2026-10-15)

Ollama `qwen2.5:3b`, 대표 13문항, 같은 코드(Ollama가 드러낸 상태 규칙 보완 후)에서 `--no-trim --full-catalogue` 켬/끔: 통과 8/13 → 11/13, 프롬프트 토큰 96,449 → 82,034(−14.9%), 판단 1회 중앙값 44 s → 49 s. 판단 시간이 같은 문항 안에서 15~180 s로 흔들려 속도 효과는 판단하지 않는다. 이전 실행에서 Ollama가 드러낸 규칙 빈틈(근거 검사 탈락·반복 정지 뒤 도구 결과가 있어도 `NEEDS_DATA`, 시간 초과 뒤 예보·가정 질문 `ANSWERED`)은 서버에서 막고 회귀 테스트를 더했다. 남은 실패 2건은 시설 상태 조회를 반복한 1건(이후 보완)과 타임라인 질문 1건이다.

전체 경로(`profile_path.py` 단독 실행, `e2e/agent-latency.spec.ts` 모델 없는 E2E 설정):

- 도구 첫 호출 → 두 번째: 기준 비교 8,316 → 41 ms, 반경 재고 5,545 → 26 ms, 연구 모델 3,112 → 1 ms, 서울 재구성 1,219 → 5 ms. 백테스트는 캐시가 없어 매번 약 160 ms.
- 브라우저: 왕복(서버 처리 제외) 30~80 ms, 응답 → 화면 17~69 ms(HAND 23 KB 응답 42 ms). 첫 호출은 반경 재고 14.4 s, 기준 비교 10.4 s, 같은 시설 두 번째 질문 82 ms.
- 메모리(Windows 작업 집합): import 197 MB → 도구 자료 전부 적재 491 MB → 요청·지도 캐시까지 611 MB. 컨테이너 상한 600 MB라 시작 시 미리 적재(H1)는 채택하지 않았고, 재배포 전 컨테이너 측정을 TODO 위험 항목으로 올렸다.

- 배포 이미지(로컬 Docker, `Dockerfile.aws`, 현재 작업 트리): 상한 없이 상시 663 MiB·최대 765 MiB. `--memory 600m`이면 상한 도달 1,086회·스왑 482 MB·Agent 요청 120초 초과(OOM 종료는 없었음, Docker Desktop은 스왑이 있음). 재배포 차단 위험으로 TODO에 올렸다.
- Gemini 재확인은 두 번 모두 일일 할당량 소진(HTTP 429)으로 무효였다(14:38 핑은 성공했지만 이어진 요청이 막힘).
- 메모리 수정 뒤 같은 흐름을 스왑 없는 600 MB 컨테이너로 다시 돌렸다. 변경 전 이미지는 첫 Agent 질문에서 OOM 종료(exit 137), 변경 후는 통과(상한 도달 0회, 정착 506 MiB, 프로세스 최대 RSS 605 MiB). 원인은 `get_osong_repository()`와 `(2023)`이 한 칸짜리 캐시의 다른 키여서 같은 오송 자료를 반복 파싱한 것이었다.
