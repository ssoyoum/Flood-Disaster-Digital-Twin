# LLM Agent·Knowledge·Kubernetes 적용 학습 로드맵

작성일: 2026-10-20

이 문서는 강의 실습을 그대로 복제하지 않고, 기존 프로젝트에서 이미 구현한 기능을 재사용해 빈 곳만 학습하기 위한 실행 순서다. **새 프레임워크를 먼저 도입하지 않는다.** 각 단계는 기준선 → 최소 변경 → 테스트/측정 → 결과 기록 순서로 진행한다.

## 프로젝트별 역할

- **ST-ROOKIE**: 교육 지식 검색, 근거 연결, LLM Wiki / GraphRAG 후보 실험의 주 대상. 현재 연결된 GitHub 도구에서 저장소가 404로 반환되어 최신 코드 확인 전까지 변경하지 않는다.
- **FloodOps (이 저장소)**: Agent 실행 경계, 서버 측 도구 검증, 진단 trace, 회귀 평가, Docker 배포 및 Kubernetes 자동 배포 연습.
- **Narrative Lab**: 온톨로지 예시를 검토할 보조 대상. 현재 Story Pack 검색은 SQLite 메타데이터 + TF-IDF lexical baseline이다. 동의어·문맥·사건 인과의 한계가 문서화되어 있으므로, 관계 모델링이 실제 검색 질문에 도움이 되는지 검증한다.

## 단계 0 — 이미 구현한 것을 기준선으로 삼기

### 확인할 기존 기능

- 등록된 도구만 실행하고 도구 입력을 서버에서 검증한다.
- 요청 시간 예산, 실패 코드, 단계별 trace와 근거 검사를 기록한다.
- 오프라인 Agent 평가 및 고정 벤치마크가 존재한다.
- Dockerfile과 docker-compose 구성이 존재한다.

### 실행할 검증

\`\`\`bash
python -m pytest backend/tests -q
npm test
npm run build
npm run test:e2e
python backend/evaluation/evaluate_agent.py --output docs/local/agent-eval-offline.json
python backend/evaluation/agent_benchmark.py --output docs/local/agent-benchmark-offline.json
\`\`\`

평가 JSON은 로컬 산출물이며 비밀키나 실제 사용자 질의를 커밋하지 않는다. 실제 Gemini 호출은 별도 승인 후 제한된 수량으로 실행한다.

**완료 조건:** 테스트 결과와 평가 JSON에서 통과율, 실패 유형, 근거 검사, p50/p95 지연(평가 결과가 제공하는 경우)을 기록한다. 이미 통과하는 기능을 중복 구현하지 않는다.

## 단계 1 — ST-ROOKIE 검색 기준선과 LLM Wiki

저장소 접근이 복구되면 실제 Retriever와 지식 저장 형식을 먼저 읽고, 기존 구조를 유지한 채 15~20개의 대표 질문으로 기준선을 만든다.

질문은 다음 유형을 포함한다.

1. 단일 문서에서 답할 수 있는 사실 질문
2. 표현은 다르지만 같은 개념을 묻는 동의어 질문
3. 두 개 이상의 개체/문서를 연결해야 하는 관계 질문
4. 자료가 없어서 답변을 보류해야 하는 질문

각 질문에 기대 근거 문서와 필수 사실을 사전에 적는다. 측정값은 근거 검색 성공률, 상위 결과 관련성, 근거 없는 답변/오답 비율, 지연 시간이다. 문서 제목·출처·갱신 시점·개체 ID를 기록해 지식이 어디서 왔는지 추적할 수 있게 한다.

**완료 조건:** 기존 검색 결과를 저장하고, 실패 질문과 실패 원인을 분류한다. ST-ROOKIE 접근 전에는 이 단계가 완료됐다고 주장하지 않는다.

## 단계 2 — Ontology / GraphRAG는 필요한 곳에만 적용

관계 질문에서 반복적으로 실패하는 사례를 추린 후, 개체와 관계를 최소 스키마로 정의한다. 예: Concept, Lesson, Evidence, Prerequisite, Explains — 실제 도메인에 맞춰 조정한다.

동일 질문 세트에서 기존 검색과 관계 기반 검색을 비교한다. 그래프를 추가해도 근거 검색 성공률이나 답변 정확도가 개선되지 않으면 도입하지 않는다. 처음부터 Neo4j를 설치하지 않고, 먼저 관계를 명시적으로 표현한 작은 데이터셋으로 검증한다.

**완료 조건:** 질문 유형별 기존 방식/관계 방식 비교표, 개선된 질문과 악화된 질문, 추가 운영 비용을 기록한다.

## 단계 3 — FloodOps Agent Harness 검증 강화

기존 도구 계약과 벤치마크를 기준으로 다음을 확인한다.

- 모델이 고른 도구와 실제 실행 도구가 일치하는가
- 잘못된 인자·범위 밖 도구·반복 호출이 차단되는가
- 근거 없는 숫자나 도구 결과에 없는 주장이 걸러지는가
- 모델 장애/시간 초과 때 NEEDS_DATA, UNAVAILABLE 등 적절한 상태로 끝나는가
- 사건 전환 및 후속 질문에서 이전 조건이 잘못 재사용되지 않는가

기존 docs/AGENT_TOOL_CONTRACTS.md, docs/AGENT_VALIDATION.md, backend/evaluation/agent_benchmark.py를 우선 재사용한다. 벤치마크 문항을 늘리기 전에 기존 평가에서 빠진 회귀 조건을 확인한다.

**완료 조건:** 변경 전·후 평가 결과, 실패 사례, 회귀 테스트가 남고 기존 테스트가 통과한다.

## 단계 4 — Docker에서 로컬 Kubernetes까지

현재 Docker/Compose 및 AWS EC2 배포 경험을 바탕으로, Kubernetes는 별도 실습 브랜치에서 작은 범위로 추가한다.

1. CI에서 백엔드 테스트와 프런트엔드 테스트/빌드를 실행한다.
2. 백엔드와 프런트엔드 이미지를 빌드하고 태그를 커밋 SHA로 고정한다.
3. 로컬 kind 또는 minikube에 배포한다.
4. Deployment/Service, 환경변수와 Secret 분리, readiness/liveness probe, CPU·메모리 requests/limits를 설정한다.
5. 새 이미지 롤아웃, 상태 확인, 실패 시 롤백을 연습한다.
6. CI에서 이미지 빌드·레지스트리 푸시까지 자동화한다. 클러스터 배포 자동화는 클러스터 접근권한과 Secret을 안전하게 구성한 후 별도 단계로 진행한다.

**주의:** 로컬 Kubernetes 배포 성공은 AWS EKS 운영 경험과 같지 않다. 실제 클러스터에 배포하지 않았다면 이력서에는 로컬 Kubernetes 실습으로만 표현한다. 현재 저장소에서 CI workflow 경로가 확인되지 않았으므로, 먼저 실제 workflow 파일 목록을 확인한 뒤 새 workflow를 추가한다.

## 단계 5 — 결과를 포트폴리오 증거로 남기기

각 실험에서 다음을 기록한다.

- 목적과 가설
- 기준선과 실험 조건
- 재현 명령
- 자동 테스트 및 평가 결과
- 실패 사례와 해결 방법
- 성능·비용·복잡성의 trade-off
- 아직 지원하지 않는 기능과 한계

완료 기준은 “기술을 사용했다”가 아니라, **왜 도입했는지, 무엇이 개선됐는지, 어떻게 재현하고 검증하는지**를 설명할 수 있는 것이다.
